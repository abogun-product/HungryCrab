# 0.6.0 release readiness

Audit date: 2026-10-21. This is a release preparation record. No acceptance criterion
is waived, no missing result is a pass, and no stable tag or publication is claimed.
The selected integration order is [#291](https://github.com/drevendev/HungryCrab/pull/291),
then [#292](https://github.com/drevendev/HungryCrab/pull/292), then the release/reopen
commit pair required by [CONTRIBUTING](../../CONTRIBUTING.md#releasing).

## Review and deterministic evidence

The audit compared the outstanding reviews on #240, #241, #246 and #259 with the
selected integration, rather than treating an empty review list on a replacement PR
as clearance of inherited findings. Neither #291 nor #292 had a submitted review at
observation time. Independent approval is not claimed by these implementation notes.

- **Stale output cleanup:** reproduced the missing refusal on Windows before the fix.
  Foundation commit `d2d3d96ae183640f0a2dc2592002a327f43a3f79` checks actual directory-entry
  spelling for every stale artifact before replacing anything. The regression preserves
  all caller bytes and the old manifest. The rule is portable to case-sensitive Linux.
- **Forged manifest ownership:** the producer/artifact sets must be equal; orphan-entry
  regressions cover ordinary and case-variant caller names.
- **Default-branch history bounds:** a real local-Git regression now switches to a branch
  diverging at a 2020 ancestor, removes the old remote default, and verifies exactly one
  reachable recent commit after `shallow=True, since="90d"` acquisition and refresh.
- **Control and publication authority:** existing tests cover maw-owned prey subsets,
  empty-list discovery, original selection provenance and merge-commit CI before tagging.
  These are CLI boundaries; they do not establish the host sandbox requested in #243.
- **In-tree staging:** a bounded regression verifies that a new nested output/staging
  directory does not alter the inventory's source listing. It passes without a staging
  implementation change. This is not closure of unrelated cache/junction safety work.

The 51 digest/acquisition tests passed locally on Windows after the fix. Ruff check,
formatting and strict mypy passed on the foundation. The new full matrix is
[foundation CI](https://github.com/abogun-product/HungryCrab/actions/runs/39604700775).
Each PR description records the final candidate SHA and its own full matrix, including
0.6's clean sdist/wheel, actual stdio MCP and portable-skill installation checks.
Recheck those SHAs before merge. Successful fork jobs do not approve upstream workflows.

## Scope decision prepared for the release owner

The current criteria require the original live work above. There is no implicit
exemption just because the requested version is 0.6 instead of 0.3.

A possible **prospective scope change**, requiring an explicit owner decision, is:
release the deterministic, human-supervised analysis surface (CLI, scoped stdio MCP,
portable skills and offline HTML), while retaining Scheduled Crab work autonomy and
learning/usefulness claims as experimental, unvalidated development functionality.
Document the accepted scope in the roadmap and milestone, preserve the open live and
quota/host-enforcement issues, and describe exactly which older criteria are deferred.
This would change the release gate; it would not complete those older milestones or
prove their exit criteria. This paragraph is a proposal, not the decision itself.

Without that decision, complete the original conditions before preparing the stable
version commits. With either route approved and its conditions satisfied:

1. Merge #291, then verify #292 contains the foundation and merge #292. Do not separately
   merge their overlapping component PRs. Recheck current heads, required CI and reviews.
2. Prepare the stable `0.6.0` commit and a separate `0.6.1.dev0` reopen commit, synchronizing
   all six version locations and dated changelog/links. Preserve both with rebase merge.
3. Verify the integrated, reopened master has green required checks. Identify the exact
   rebased stable commit, check its versions/changelog and tag that ancestor `v0.6.0`.
4. Require a completed green tag matrix before creating the stable GitHub Release and
   separate plugin tag. Build the sdist/wheel from the verified release commit.
5. Publish with owner-authorized PyPI credentials or a configured
   [Trusted Publisher](https://docs.pypi.org/trusted-publishers/using-a-publisher/).
   Verify the published files, hashes and a fresh Windows/Linux install from the index.
   Record actual release URLs and evidence before updating any release-completion claim.
